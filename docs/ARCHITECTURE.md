# Архитектура

## Слои

```text
React UI (src/pages)
  ├─ общие диалоги, формы, графики (src/components)
  ├─ форматирование / управленческие метрики (src/lib.ts)
  └─ StoreProvider: состояние, ошибки, повтор запросов
           │ same-origin HTTP + CSRF + idempotency key
Express API (server/index.ts)
           │ валидация команд
StoreService (shared/service.ts; server/service.ts — реэкспорт)
           │ BEGIN IMMEDIATE → изменения + журнал + ключ запроса → COMMIT
SQLite (server/db.ts)
```

В локальном режиме React не меняет баланс напрямую: все операции выполняет сервер. После успешной команды возвращается новое согласованное состояние. В MVP `/api/state` передаёт весь набор данных; для больших объёмов потребуются пагинация, серверные выборки и отдельные агрегаты.

## GitHub Pages: отдельный режим демонстрации

Сборка `--mode demo` подставляет браузерный адаптер `src/demo/client.ts` вместо HTTP. Он лениво загружает sql.js/WebAssembly и выполняет **тот же** `shared/service.ts`, `shared/database.ts` и `shared/seed.ts`. Сервер продолжает использовать native `node:sqlite`; браузер — `shared/wasm-database.ts`. SHA-256 одинаков в обоих режимах и совместим с сохранёнными ключами запросов.

База экспортируется целиком в IndexedDB `florist-market-demo-v1`. Чтение актуального снимка, синхронная SQL-транзакция и запись нового снимка происходят внутри одной readwrite-транзакции IndexedDB. Она сериализует изменения из нескольких вкладок; UI получает успех только после `oncomplete`. Ошибка прерывает запись и сохраняет предыдущую версию. Восстановление вкладки обновляет состояние.

Это способ просмотреть и испытать MVP, а не общая облачная база. Нет синхронизации устройств, авторизации, передачи платежей и серверной защиты от редактирования данных владельцем браузера. Подходит только для тестовых данных. Полный экспорт базы на каждую операцию ограничивает размер демо; для реальной эксплуатации нужен защищённый сервер.

## Модель данных

- `products`: SKU, штрихкод, наименование, категория, размер, цвет, единица, остаток, минимальный запас, цена и средняя себестоимость.
- `recipes`: изделие, версия, материальные нормы, норматив труда и накладных.
- `production`: партия, плановая дата, статус, снимок спецификации, материальная стоимость запуска, итоговая стоимость выпуска.
- `sales`: смена, покупатель, способ оплаты, скидка, сумма, себестоимость и JSON-снимок строк. Строка содержит исходные SKU, название, цену, netPrice, себестоимость, проданное и возвращённое количество.
- `returns`: ссылка на исходную продажу и текущую смену, возвращённые количества, сумма, себестоимость, причина.
- `shifts`: размен, время открытия/закрытия, ожидаемые и пересчитанные наличные.
- `ledger`: подписанные суммы; типы sale / return / stock / income / expense / debt. Списание запасов — специальная неденежная категория expense.
- `debts`: контрагент, направление, сумма, погашение, срок.
- `movements`: каждое изменение остатка со ссылкой на операцию.
- `audit`: действие, сущность, описание и время. Журнал обычный, не криптографически защищённый.
- `requests`: UUID запроса, SHA-256 содержимого команды и сохранённый результат для идемпотентности.

Это схема v1 (`PRAGMA user_version=1`). При будущих изменениях схемы нужны нумерованные миграции и тест восстановления; `CREATE TABLE IF NOT EXISTS` не заменяет миграции существующих колонок.

## API

- `GET /api/health` — состояние процесса.
- `GET /api/state` — данные, `mode: demo`, текущее серверное время и CSRF-токен.
- `POST /api/operations/:operation` — команда с JSON и заголовками `X-CSRF-Token`, `Idempotency-Key` (UUID).

Команды:

```text
product.save       stock.adjust       recipe.save
production.create  production.start   production.complete  production.cancel
shift.open         shift.close
sale.create        sale.return
finance.create     debt.create        debt.pay
```

Все суммы API — копейки; остатки и нормы — тысячные; `quantity` продажи/производственного заказа — целое число изделий. Ответ команды: `{ result: { id, ... }, state: {...} }`. Ошибки: 400 (валидация), 403 (Host / Origin / CSRF), 409 (бизнес-правило), 500 (непредвиденная ошибка). Неизвестный API-маршрут — 404.

Один UUID с тем же телом вернёт сохранённый результат. С другим телом — ошибка. Клиент сохраняет UUID для повтора неуспешного сетевого запроса в текущем сеансе страницы. После перезагрузки страницы сначала проверьте журнал продаж: UUID незавершённого запроса не сохраняется на диск. Надёжная очередь с восстановлением после закрытия браузера — отдельная доработка для реального POS.

## Транзакционные границы

Продажа: проверить смену → проверить корзину → списать все товары → сохранить строки и себестоимость → записать денежное движение → журнал → ключ запроса. При ошибке любой строки откатываются все предыдущие изменения.

Возврат: проверить открытую смену → проверить непревышение проданного количества → вернуть товары по исторической себестоимости → проверить доступность наличных → сохранить возврат → уменьшить денежный поток. Полный возврат — сумма оставшихся количеств, отдельной логики нет.

Производство: создание сохраняет спецификацию; запуск списывает сырьё и замораживает материальную стоимость; выпуск добавляет нормативные труд/накладные и увеличивает остаток изделия. Повторный запуск/выпуск запрещён состоянием и идемпотентностью.

SQLite `BEGIN IMMEDIATE` сериализует изменения между соединениями. Одновременно открыта одна смена (частичный уникальный индекс); остаток не может быть отрицательным. Деньги и количества валидируются и ограничены по размеру.

## Безопасность

- Привязка сервера к `127.0.0.1`; разрешён Host только localhost/127.0.0.1 с портом экземпляра.
- Проверка Origin / Sec-Fetch-Site; CSRF-токен на изменениях. Это защита от другого сайта, **не авторизация локального пользователя**.
- SQL-параметры для всех пользовательских значений, ограничение JSON 100 KB, валидация Zod. Имена таблиц/команд задаются кодом.
- React экранирует текст; HTML от пользователя не вставляется.
- Production CSP, запрет iframe, nosniff, запрет кеширования API.
- CSV экранирует ячейки и нейтрализует формулы. Нет секретов, внешней аналитики, платёжных ключей или реальных реквизитов.
- Любой пользователь с локальным доступом к компьютеру может читать базу. Шифрование, роли, персональные сессии и журнал идентичностей отсутствуют.
- Внешние ссылки в справке используют `rel=noreferrer`.

## Интеграции следующего этапа

1. Адаптер ККТ: отдельные команды с устойчивым `externalId`, очередь заданий, состояния pending / fiscalized / failed / unknown, сверка с ФН, повтор по тому же ключу. Тайм-аут нельзя трактовать как отсутствие чека.
2. Эквайринг/СБП: подтверждение провайдера, подписанные события, уникальные transactionId, возвраты и сверка банка. Выбор кнопки «Карта» в MVP не означает успешную оплату.
3. Бухгалтерия: организация и налоговый режим, первичка, ставки/признаки НДС по строкам и дате, справочники контрагентов, план счетов, обмен с 1С или другой системой, закрытие периода.
4. Производство: фактический расход, брак/отходы, частичный выпуск, зарплата и накладные с распределением отклонений; связь долгов, закупок и начислений с документами.
5. Многопользовательский доступ: роли кассир / кладовщик / производство / бухгалтер / владелец, серверные права и аудит, миграция на PostgreSQL при необходимости.
